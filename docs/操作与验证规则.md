# 操作与验证规则

生效日期：2026-11-01。适用于本项目所有操作，包括读取和排查、方案与预览、绘图与素材、代码与配置、构建导出、测试验证、Git、打包发布以及文档规则维护。用户最新明确要求优先；本文不自动授权修改、提交、回滚或发布。

## 1. 操作前先读规则

- 每项操作开始前，先读取 [项目协作规则](../AGENTS.md) 和本文，再根据协作规则的必读索引读取所有相关专项规则的完整内容；读取规则本身是流程起点，不递归增加前置流程。
- 在设计方案、绘图或制作预览前完成阅读，不能先做预览后补读，也不能先改正式内容后补读。只读检查与问题排查在读取相关规则后即可开展，不因检查本身要求额外预览确认。
- 开始操作时简要说明实际读取并采用的规则；不得把文件名、索引或摘要当作已经读过正文。规则更新或操作范围变化时，先重新读取受影响的规则，再继续操作。
- 多类操作同时适用多份规则。例如图集生成并接入游戏，需读取绘图与素材、渲染与加载、编码规则；Boss、地图、怪物展示、异常状态特效再叠加各自专项规则。
- 未被索引点名的工作仍受公共规则约束，按实际内容补读相关专项规则。缺少必要约定时，在独立方案预览中说明拟采用的要求；不得自行假定已获准新增功能或改变现有表现。
- 用户最新明确指令优先。公共流程与专项要求同时生效；专项尺寸、锚点等约定不能被通用素材建议覆盖。发现不能同时满足的冲突时，说明具体条款及影响，先推进不受冲突影响的工作。

## 2. 确认与操作范围

- 正式修改沿用“先读规则 → 核对当前内容 → 制作独立预览 → 等待明确确认 → 在确认范围内实施 → 验证”的顺序。此要求覆盖文档和规则本身。
- 已确认方案可直接在确认范围内完成，不重复索要同一授权；增加或改变方案的部分先另行预览确认。
- 只读检查不能悄悄变成修复、覆盖资源或修改配置。检查发现的问题先如实报告；需要修改时按已有授权范围与预览流程处理。
- 区分概念方案、临时演示、正式实现、Git 提交与线上发布。完成其中一步不代表其他步骤已经获准或已经完成。

## 3. 文件、命令与工具

- 操作前核对当前分支、相关文件状态和目录归属，保留已有未提交修改；不要用旧内容覆盖当前工作区，也不要把不相关的修改混入本次交付。
- 运行命令前先了解其输入、输出与副作用。构建、导出、素材整理和部分测试会写文件，不能仅凭名称将其视作只读操作；先查看对应脚本及区域说明。
- 预览与诊断输出写入独立临时位置或项目约定的预览目录。已确认实施中的构建与验证可在确认范围内运行；可能额外覆盖正式素材、运行配置或发布目录时，不能作为“顺便验证”执行。
- 原始素材、可编辑源数据、构建产物和发布副本区分管理。重新生成前核对主从关系及手工修改，清理或覆盖前确认目标路径和影响范围。
- 新增和修改代码、样式、脚本、测试代码、构建及运行配置前，同时读取 [编码规则](编码规则.md)，按一批修改更新游戏版本和相关缓存引用。仅改规则文档不强制提升版本。

## 4. 按改动选择验证

- 先读取被验证对象的专项规则和当前验证脚本，使用与本次变化相关的检查；不可用过期版本断言或旧效果当作最新验收标准。
- 只改文档时检查链接、适用范围、表述一致性和与现有规则的冲突；不为纯文档维护运行整套游戏回归。
- 修改代码时执行相关逻辑、功能和兼容性检查；素材或布局变化增加当前镜头与手机尺寸下的实机检查，动作变化检查过程、遮挡、暂停及循环，而非只看静态截图。
- 渲染与加载变化同时遵守 [渲染与加载规则](渲染与加载规则.md)，分别记录环境、帧耗时、加载阶段与内存估算；桌面模拟结果不得冒充真机数据。
- 检查失败先定位原因。若因加载方式等行为变化需要调整测试，应继续验证原本要保障的行为，不能只删掉失败断言；不得把测试通过等同于视觉已确认。
- 相关检查通过后，不无故扩大或重复测试；如又修改代码、出现失败或仍有明确疑点，再补充对应验证。

## 5. Git、回滚、打包与发布

- 提交、推送、回滚、打标签、打包与发布前，先读本文和 [编码规则](编码规则.md)，核对实际授权、目标分支或目录、当前版本和包含的文件。
- 不因用户要求修复或完成本地实现，就自动提交、推送或发布；也不因规则列出某项操作，就视为取得该操作的授权。已明确授权的动作按范围继续完成，不重复询问。
- 回滚前核对目标提交或备份、当前差异及需要保留的内容；不得自行扩大为整仓库重置或丢弃未提交工作。回滚方案仍按项目预览确认流程执行。
- 构建与打包前核对正式输入和输出目录；发布前完成适用检查，Git 提交标题使用本批最终游戏版本。历史记录中的版本不批量替换为当前版本。

## 6. 文档、规则维护与交付

- 修改某项规则前，先读项目协作规则、本文、该规则全文及直接相关规则；核对新增要求是否与当前授权和其他专项要求冲突。
- 新增专项规则时同步更新协作入口和必要的互相引用；扩展适用范围时同时覆盖新建与已有内容修改，不能只写“制作新内容前”。
- 文档区分规范要求、已实现状态、历史记录和待实施事项。不能因为写了规则就宣称已落实，或因当前代码尚未满足规则就擅自迁移。
- 交付说明实际修改、验证结果和限制；包含代码时注明最终游戏版本，说明是否已提交或发布。只读检查不把建议描述成已经修改，未执行的验证不宣称通过。
