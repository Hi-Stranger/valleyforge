# 操作与验证规则

生效日期：2026-11-01。适用于本项目所有操作，包括读取和排查、方案与预览、绘图与素材、代码与配置、构建导出、测试验证、Git、打包发布以及文档规则维护。用户最新明确要求优先；本文不自动授权修改、提交、回滚或发布。

## 1. 操作前先读规则

- 每项操作开始前，先读取 [项目协作规则](../AGENTS.md) 和本文，再根据协作规则的必读索引读取所有相关专项规则的完整内容；读取规则本身是流程起点，不递归增加前置流程。
- 在设计方案、绘图或制作预览前完成阅读，不能先做预览后补读，也不能先改正式内容后补读。只读检查与问题排查在读取相关规则后即可开展，不因检查本身要求额外预览确认。
- 开始操作时简要说明实际读取并采用的规则；不得把文件名、索引或摘要当作已经读过正文。规则更新或操作范围变化时，先重新读取受影响的规则，再继续操作。
- 多类操作同时适用多份规则。例如图集生成并接入游戏，需读取绘图与素材、渲染与加载、编码规则；Boss、地图、怪物展示、异常状态特效再叠加各自专项规则。
- 未被索引点名的工作仍受公共规则约束，按实际内容补读相关专项规则。缺少必要约定时，在独立方案预览中说明拟采用的要求；不得自行假定已获准新增功能或改变现有表现。
- 用户最新明确指令优先。公共流程与专项要求同时生效；专项尺寸、锚点等约定不能被通用素材建议覆盖。发现不能同时满足的冲突时，说明具体条款及影响，先推进不受冲突影响的工作。

## 2. 确认与操作范围

- 正式修改沿用“先读规则 → 核对当前内容 → 制作独立预览 → 等待明确确认 → 在确认范围内实施 → 验证”的顺序。此要求覆盖文档和规则本身。
- 已确认方案可直接在确认范围内完成，不重复索要同一授权；增加或改变方案的部分先另行预览确认。
- 只读检查不能悄悄变成修复、覆盖资源或修改配置。检查发现的问题先如实报告；需要修改时按已有授权范围与预览流程处理。
- 区分概念方案、临时演示、正式实现、Git 提交与线上发布。完成其中一步不代表其他步骤已经获准或已经完成。

## 3. 文件、命令与工具

- 操作前核对当前分支、相关文件状态和目录归属，保留已有未提交修改；不要用旧内容覆盖当前工作区，也不要把不相关的修改混入本次交付。
- 运行命令前先了解其输入、输出与副作用。构建、导出、素材整理和部分测试会写文件，不能仅凭名称将其视作只读操作；先查看对应脚本及区域说明。
- 预览与诊断输出写入独立临时位置或项目约定的预览目录。已确认实施中的构建与验证可在确认范围内运行；可能额外覆盖正式素材、运行配置或发布目录时，不能作为“顺便验证”执行。
- 原始素材、可编辑源数据、构建产物和发布副本区分管理。重新生成前核对主从关系及手工修改，清理或覆盖前确认目标路径和影响范围。
- 新增和修改代码、样式、脚本、测试代码、构建及运行配置前，同时读取 [编码规则](编码规则.md)，按一批修改更新游戏版本和相关缓存引用。仅改规则文档不强制提升版本。

## 4. 按改动选择验证

- 先读取被验证对象的专项规则和当前验证脚本，使用与本次变化相关的检查；不可用过期版本断言或旧效果当作最新验收标准。
- 只改文档时检查链接、适用范围、表述一致性和与现有规则的冲突；不为纯文档维护运行整套游戏回归。
- 修改代码时执行相关逻辑、功能和兼容性检查；素材或布局变化增加当前镜头与手机尺寸下的实机检查，动作变化检查过程、遮挡、暂停及循环，而非只看静态截图。
- 渲染与加载变化同时遵守 [渲染与加载规则](渲染与加载规则.md)，分别记录环境、帧耗时、加载阶段与内存估算；桌面模拟结果不得冒充真机数据。
- 检查失败先定位原因。若因加载方式等行为变化需要调整测试，应继续验证原本要保障的行为，不能只删掉失败断言；不得把测试通过等同于视觉已确认。
- 相关检查通过后，不无故扩大或重复测试；如又修改代码、出现失败或仍有明确疑点，再补充对应验证。

## 5. Git、回滚、打包与发布

- 提交、推送、回滚、打标签、打包与发布前，先读本文和 [编码规则](编码规则.md)，核对实际授权、目标分支或目录、当前版本和包含的文件。
- 不因用户要求修复或完成本地实现，就自动提交、推送或发布；也不因规则列出某项操作，就视为取得该操作的授权。已明确授权的动作按范围继续完成，不重复询问。
- 回滚前核对目标提交或备份、当前差异及需要保留的内容；不得自行扩大为整仓库重置或丢弃未提交工作。回滚方案仍按项目预览确认流程执行。
- 构建与打包前核对正式输入和输出目录；发布前完成适用检查，Git 提交标题使用本批最终游戏版本。历史记录中的版本不批量替换为当前版本。

## 6. 文档、规则维护与交付

- 修改某项规则前，先读项目协作规则、本文、该规则全文及直接相关规则；核对新增要求是否与当前授权和其他专项要求冲突。
- 新增专项规则时同步更新协作入口和必要的互相引用；扩展适用范围时同时覆盖新建与已有内容修改，不能只写“制作新内容前”。
- 文档区分规范要求、已实现状态、历史记录和待实施事项。不能因为写了规则就宣称已落实，或因当前代码尚未满足规则就擅自迁移。
- 交付说明实际修改、验证结果和限制；包含代码时注明最终游戏版本，说明是否已提交或发布。只读检查不把建议描述成已经修改，未执行的验证不宣称通过。

## 7. AI 游戏智能体协作与模型路由

- 完整游戏或可玩切片按游戏总监流程组织，先识别任务阶段、职责、风险与验收条件，再按需分派；单项任务直接交给对应专长，不强制并行。主代理负责拆分、协调、检查结果与关键判断，子代理只处理分配范围。适用技能及项目规则仍须读取。
- 调度优先级：本地程序处理可自动化的试玩、截图、数值计算、素材处理和配置检查；简单文档、批量内容、测试复现和局部修复优先 GPT-6 Luna；常规复杂策划、架构、开发、视觉验收和发布审查优先 GPT-6.1 Terra。按难度选择能可靠完成任务的最低层级，不必机械逐级尝试。
- 默认角色与推理档位：总监 director、架构 architect、发布审查 release-reviewer 使用 gpt-6.1-terra / high；复杂开发 developer、视觉审查 visual-reviewer 使用 gpt-6.1-terra / medium；内容 content-worker、测试 qa-tester 使用 gpt-6-luna / low；素材 asset-worker、局部修复 bug-fixer 使用 gpt-6-luna / medium。职责按当前项目和可用工具调整；这些角色与档位是调度目标，并不表示本项目已配置这些角色或能自动切换。
- 仅在有明确证据表明 Terra 无法可靠完成时，对确需升级的部分使用 GPT-6.2 Sol；记录原因、已尝试方案与相关证据，问题解决后恢复 Terra 或 Luna。Sol Ultra 是上限，仍无法解决时拆分任务、调整方案或记录阻塞。普通问题最多两次有效修复，避免无意义重复；不以此代替项目要求的必要验证。
- 禁止所有 Astra 系列，覆盖主代理、子代理、继承、自动路由、备用模型及 Skills、MCP 的独立语言模型调用；调用前确认实际模型合规，无法确认时不调用。未经授权不启用额外付费 API 或加速模式；已授权专业图片生成工具不受语言模型等级限制。
- 分派时传递必要的目标、规则、路径、限制、证据与验收条件；按阶段简要交接并复用结果，避免无关完整历史、重复分工和无依据的反复测试。使用低成本模型不降低用户确认的范围、审美标准或验收要求。
- 模型与档位实际能否选择取决于当前客户端、平台权限及更高优先级配置；无法使用指定模型时，不假定已完成切换，报告实际可用选项和限制。模型配置只能提供默认值，不承诺切换已运行的主会话、阻止客户端覆盖或拦截第三方内部路由。当前模型实际价格和额度不可见时，不声称已核实具体价格或剩余额度。
- 按任务设定图像生成次数、迭代轮数和测试运行上限，必要时记录调整原因；继续遵守项目预览确认流程和专项规则。

## 8. 审美方向与视觉验收

### 8.1 适用范围与优先级

- 本节适用于新游戏、重制、新区域、现有场景或素材的视觉修改，以及审美评审。按变更范围选择检查维度；地图、Boss、怪物展示、UI、素材、渲染等专项规则同时生效，用户最近明确确认的效果及专项固定要求优先。纯规则维护不冒充游戏视觉验收。
- 先读项目协作与适用规则，核对实际实现、可用素材和已有证据；既有项目在受影响场景保存同镜头、同分辨率的当前实机基线。发布副本缺少源文件或参考时明确记录，不猜测缺失内容，也不虚构已确认标准。
- 任何修改仍须先制作独立预览并等待用户明确确认。目标图、概念图、静态预览和技能说明动画是设计或交接材料；它们不等于运行版本、实机截图或最终验收证据。

### 8.2 建立目标与参考

- 新视觉体系或重制先整理一页视觉方向：主题与情绪、玩家与镜头、视觉锚点、构图和路线、色彩与明暗、光源、轮廓、材质、画面层次、HUD 安全区、参考来源、资产清单及需要保持的已有元素。目标图使用最终游玩视角；区域总览不能代替正常镜头预览。
- 新游戏需要外部参照时，检查 3–5 个相关游戏的真实游玩画面；优先开发者发布的实机帧，记录作品、场景、状态和来源，只借鉴构成原理。已有项目优先使用用户最近确认的区域效果和可用的项目实机证据；不得未经授权复制他人素材。
- 当前项目沿用固定斜俯视二维像素风，保持人物、怪物、环境的像素尺度、视角与正常游玩比例；新区域可按主题调整配色，须与已确认作品协调。设计参考不能自行替换现有人物或改变探索遇敌后进入独立战斗的结构。

### 8.3 视觉设计检查

- 构图与空间：玩家、敌人、道路、可交互目标和重要地标有明确视觉层次；保留可行走、可观察和可闪避空间。地表低噪声，景物疏密有节奏，避免均匀撒满、规则条纹、无意的空旷或因装饰阻挡动线；地图实际碰撞与视觉通行一致。
- 轮廓与比例：玩家、普通怪、Boss 和交互物在正常镜头下可区分；同一对象跨动画帧保持身份、体量、锚点与主要轮廓，脚部接地可信。只借鉴已有确认画面与专项规则，不将其他游戏的角色尺寸或构图固定值套入本项目。
- 色彩、明暗与材质：背景、可走地面、障碍和交互信息具备可辨层次；高饱和或强对比优先用于关键目标和预警，环境变化服务于主题。保持低噪声地表、自然边缘、协调的光照方向与像素尺度；避免素材之间明暗、描边或质感明显割裂。
- 深度与遮挡：检查角色脚点与树木、桥、水面、前景的遮挡关系，移动时不出现错误穿插、跳动或无意裁切。像素素材按现有渲染规则采样；不能为修饰画面破坏已确认比例、色彩、动作或遮挡。
- UI 与可读性：在桌面和适用的手机横屏视口检查文本、按钮、重要数值与操作区域；控件、通知、景物与特效不得遮挡玩家、敌人、预警或关键输入。怪物和 Boss 头顶展示、尺寸、名称与战斗内外显隐严格遵守对应专项规则。
- 动作与反馈：按实际变化检查起手、预警、命中、躲避、落地、收势及暂停；角色和危险区域在动态过程中始终可辨。特效、震动和光晕服务动作与反馈，不靠叠加粒子掩盖构图、素材或动作问题；Boss 攻击提示和判定遵守 Boss 规则。

### 8.4 代表场景与实机证据

- 新游戏、重制或需建立新视觉体系的区域，确认方案后先用正式可追溯资产制作能操作的代表场景，覆盖主要玩法和关键反馈；代表场景通过本节验收后再批量扩充同类内容。已有场景局部修改只检查受影响部分和必要回归，不强制整体重制。
- 从真实可运行构建或发布入口，以实际输入走到目标状态；按任务记录版本、设备与浏览器、分辨率、缩放、镜头、场景、输入路径、游戏状态、素材错误及相关性能。桌面模拟不能当作手机真机，技能说明动画不能当作实机录像。
- 保留原始目标图、修改前实机图、每轮修改后实机图；动态变化补充关键动作序列或实机录像。对照尽量保持场景、镜头、视口、缩放及可比状态一致；状态无法对齐时记录差异。差异图或像素比对用于定位，不能替代人工视觉判断。

### 8.5 分项评分与通过条件

- 对本次实际涉及的维度逐项评分：整体风格统一、构图与动线、角色及物件比例、场景丰富度、光影、色彩、材质与像素一致性、UI/HUD、深度遮挡、动画、战斗可读性、镜头和特效、目标设备适配。每项关联具体实机截图或动作序列及观察说明；与本次变更无关的维度写明不适用原因，缺少证据标为未验证，不得用不适用掩盖缺失。
- 评分含义：1 分为严重缺陷或阻断，2 分为明显偏离，3 分为需要修正，4 分为符合项目要求，5 分为充分符合。没有实现或缺少证据分别标记为缺失或未验证，不以 0 分、平均分或其他项目的历史分数代替证据。
- 通过线：所有适用维度均至少 4/5；不存在未解决的重大或阻断问题；本次适用的玩法与运行检查通过；按项目要求完成用户确认。一个适用维度未达标或未验证即不能宣称整体通过，不用平均分抵消。评分是审查记录，不能覆盖用户最新明确意见或专项固定标准。
- 重大或阻断问题包括玩家或攻击预警难以辨认、关键 UI 遮挡操作、明显错误遮挡或素材缺失、关键玩法无法验证，以及违反已确认方案的明显差异。记录问题位置、证据、影响、严重程度、责任范围、修复状态和复测结果。

### 8.6 修复、回归与交付

- 先比较构图与镜头、比例、轮廓、色彩与明暗、材质和光源，再处理装饰、粒子或后期；按对玩法和整体效果的影响排序。每轮优先定位并修正一个主要根因，保持比较条件，必要时控制变量，再记录前后证据及未对齐之处。
- 审美初检按项目智能体路由选择能胜任的低成本角色；专业评分、复杂问题或发布冲突按路由升级。优先复用现有截图和比较工具，设置并记录生成、迭代和测试上限；不因节省额度跳过必要检查或降低验收标准。
- 用户认可、稳定、可追溯的实机图或录像可保存为后续回归基线，记录对应版本、环境、状态及证据类型。交付说明逐项评分、未验证项、未解决问题、实际测试与环境限制；测试通过不代表视觉已获确认。

## 9. 开发交接、资产和验收证据

- 对新增或改变的玩法，以适用程度记录玩家目标、核心循环、输入、关键状态、成功与失败条件、重试和反馈；设计、实现及验证使用同一份已确认范围，不将未实施方案写成现有功能。
