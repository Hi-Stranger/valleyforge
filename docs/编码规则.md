# 编码规则：版本号与 Git 提交

生效日期：2026-10-29。适用于本项目后续代码修改与 Git 提交；用户最新的明确指令优先。

## 所有修改的前置流程

遵守 [项目协作规则](../AGENTS.md) 中“所有修改必须先预览、确认后实施”的要求。先提供静态预览图、GIF 或变更说明图，等待用户查看并明确确认当前方案后再实施。即使用户直接要求修改代码或直接实现，也不能跳过该流程；不得先修改正式内容再补预览。此要求覆盖代码、配置、脚本、素材及文档规则等所有修改。

## 每次修改代码必须更新游戏版本号

- 每批交付的代码修改都必须提升一次游戏版本号，包括功能、修复、重构、样式、构建脚本、测试脚本和运行配置修改。一次任务中的连续编辑、修错和验证可合为一批，不要求每次保存文件都提升版本。
- 分成多个代码提交时，每个包含代码修改的提交都必须携带新的游戏版本号，不能沿用上一代码提交的版本。
- 仅修改说明文档、协作规则或生成概念预览，不强制提升游戏版本。本次新增规则属于文档修改。
- 提升前读取工作区当前版本和最近 Git 历史；保留已有未提交修改，不能用旧版本覆盖他人的新版本。

## 版本格式与同步位置

- 沿用现有游戏版本格式 `YYYY.MM.DD.N`，例如 `2026.10.29.3`；展示时可加 `v`。
- 日期以用户所在时区 Asia/Singapore 为准。同日将序号递增；日期前进后从 `1` 开始；不得因系统时间不同而回退版本。
- 游戏版本以 `game/main.mjs` 的 `GAME_VERSION` 为准。编写本文时读到的值为 `2026.10.29.3`，此值只是当时记录，后续必须重新读取。
- 同步更新 `index.html` 中已有的游戏资源版本查询参数，使其与最终 `GAME_VERSION` 一致。新增需要随本轮更新刷新的资源时，按项目现有加载方式处理缓存。
- 检查其他运行入口、发布构建和验证脚本中的相关版本引用。固定断言旧游戏版本的测试应随版本更新；历史说明、备份和旧发布记录无需批量替换。
- `package.json` 的 `version` 当前为独立的 npm 语义版本（`0.2.0`），不将日期游戏版本写入该字段。本规则要求每次提升的是可见游戏版本；如另行调整 npm 包版本，需同步 `package-lock.json` 顶层及根包版本。
- 存档结构中的 `version` 是数据格式版本，不能为了显示版本更新而修改；只有明确需要存档迁移时才另行处理。

## Git 提交必须带最终版本号

- 在代码完成、最终版本号确定并完成必要验证后，才形成提交。
- 提交标题统一为：`v<最终游戏版本号> <本次修改摘要>`。
- 示例：`v2026.10.29.4 修复手机横屏全屏入口`。示例版本不能直接照抄，必须取本次实际最终版本。
- 若同一轮修改中版本再次递增，提交标题使用最后一个版本，不能填写任务开始时的旧版本。
- 纯文档等不提升版本的提交，也在标题中带上工作区当前的最终游戏版本，例如 `v2026.10.29.3 补充项目编码规则`。
- 提交正文可补充改动和验证结果；标题必须已经包含版本号，不能只写在正文或 Git 标签中。
- 提交前核对暂存内容里的 `GAME_VERSION`、资源版本引用和提交标题一致，不能只更新工作区却漏暂存版本文件。
- 本规则规定提交格式，不意味着每次修改都自动提交、推送、打标签或发布。是否执行这些动作按用户指令和当前任务范围决定。

## 修改完成时检查

1. 确认是否包含代码修改；如包含，已提升游戏版本。
2. 核对游戏显示版本、相关入口缓存参数和适用的版本断言。
3. 运行与改动相关的检查，明确报告未执行或未通过的项目。
4. 如果执行 Git 提交，核对暂存版本，并用 `v<最终游戏版本号> 摘要` 作为提交标题。
5. 向用户报告代码改动时注明最终游戏版本；未提交则如实说明，不把本地修改描述成已提交或已发布。
